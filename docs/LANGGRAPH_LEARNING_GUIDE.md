# LangGraph 学习路线：从入门到理解源码

适用对象：有一点 Python 基础，希望既会使用 LangGraph，也能理解源码的学习者。

推荐顺序：**做小实验 → 理解运行机制 → 带着问题读源码 → 做完整项目**。每个阶段都留下可运行的成果，以验收结果衡量进度。

本文依据当前下载的仓库与学习讨论整理。仓库版本和在线文档可能发生变化，遇到接口差异时，核对实际安装版本及本地实现。

## 1. 先建立核心认识

**LangGraph 管理的是一个有状态、可以分支和循环的执行过程。** 节点可以调用模型，也可以只是普通 Python 函数。持久化、中断恢复和流式输出都是它的重要能力。

参考：[官方概览](https://docs.langchain.com/oss/python/langgraph/overview)。

用“文章修改助手”贯穿整个学习过程：

```text
输入文章 → 检查文章 → 判断是否达标 → 输出结果
              ↑            │
              └── 修改文章 ←┘
```

围绕这个流程，先想清楚六个问题：

| 概念 | 应该问自己的问题 |
| --- | --- |
| State，状态 | 执行到这里，后续步骤需要知道什么？ |
| Node，节点 | 这一步承担什么职责，返回哪些更新？ |
| Edge，边 | 下一步去哪里，由什么条件决定？ |
| Reducer，更新合并规则 | 新值应该覆盖旧值，还是累加、合并？ |
| Checkpoint，检查点 | 需要保留哪些执行信息，才能继续运行？ |
| Interrupt，中断 | 哪里需要等待人来做决定？ |

第一阶段重点掌握状态、节点、边和更新合并规则。

参考：[Graph API 文档](https://docs.langchain.com/oss/python/langgraph/graph-api)。

## 2. 分阶段学习计划

按每天一小时估算，约两到三周。以验收结果为准，不必赶天数。

| 阶段 | 建议时间 | 动手任务 | 验收标准 |
| --- | --- | --- | --- |
| 基础流程 | 2～3 天 | 用普通函数做两节点串联，再加入条件分支和循环 | 不看教程，能写一个会按条件结束的图 |
| 状态管理 | 3～4 天 | 增加修改次数和修改记录，比较覆盖与累加 | 运行前能预测每一步状态，并解释结果 |
| 恢复与交互 | 3～4 天 | 加检查点、人工审核、中断恢复，再尝试流式输出 | 能解释同一线程如何继续执行，以及恢复时哪些代码可能重跑 |
| 接入模型 | 4～5 天 | 把检查或修改节点替换成模型调用，加入失败处理和测试 | 能区分流程错误、模型输出错误、外部服务错误 |

### 阶段一：基础流程

- [ ] 使用普通 Python 函数实现两个节点串联。
- [ ] 加入条件分支，决定直接输出还是进入修改。
- [ ] 加入循环，修改后重新检查。
- [ ] 设置明确的退出条件，例如最多修改三次。
- [ ] 合上示例，独立重写并解释流程。

这一阶段不需要 API Key，也不需要数据库。使用固定规则，便于预测和检查结果。

### 阶段二：状态管理

- [ ] 明确文章内容、修改次数、检查结果和修改记录等状态字段。
- [ ] 明确每个字段由哪个节点更新。
- [ ] 实验节点只返回部分字段时，其他字段如何保留。
- [ ] 比较字段覆盖与使用 reducer 累加的效果。
- [ ] 运行前写下预期状态，运行后逐步核对。

### 阶段三：恢复与交互

- [ ] 使用内存检查点理解状态保存机制。
- [ ] 理解线程标识与执行状态之间的关系。
- [ ] 在输出前加入人工审核和中断恢复。
- [ ] 检查恢复时哪些代码会重新执行。
- [ ] 尝试流式输出，观察执行过程。
- [ ] 使用 SQLite 等持久化实现，验证退出程序后继续执行。

内存检查点适合学习机制，不能承担跨进程保存。需要验证程序退出后恢复时，再接入持久化实现。

### 阶段四：接入模型

- [ ] 把一个固定规则节点替换成模型调用。
- [ ] 保留可预测的流程控制和退出条件。
- [ ] 验证模型返回内容不符合预期时的处理。
- [ ] 主动模拟异常、超时和重复执行。
- [ ] 为关键流程编写有实际意义的测试。
- [ ] 独立解释一次完整执行，包括状态变化和失败路径。

## 3. 源码阅读顺序

前期主要接触 `libs/langgraph` 和 `libs/checkpoint`。`prebuilt`、SDK、CLI 等到具体需要时再看。

| 顺序 | 源码入口 | 带着什么问题读 |
| --- | --- | --- |
| 1 | [graph/state.py](libs/langgraph/langgraph/graph/state.py) 中的 `StateGraph` | 如何记录状态、节点和边？ |
| 2 | [graph/state.py](libs/langgraph/langgraph/graph/state.py) 中的 `compile()` | 图定义如何转成可以执行的对象？ |
| 3 | [test_state.py](libs/langgraph/tests/test_state.py) | 框架用哪些输入和断言保证状态行为？ |
| 4 | [types.py](libs/langgraph/langgraph/types.py) | `Command` 与 `interrupt` 如何表达控制流程？ |
| 5 | [内存检查点实现](libs/checkpoint/langgraph/checkpoint/memory/__init__.py) | 一次执行到底保存了什么？ |
| 6 | [pregel/main.py](libs/langgraph/langgraph/pregel/main.py) | 运行时如何组织图的执行？ |

`pregel` 涉及更多内部细节，放在已经会写分支、循环和恢复流程之后学习。

每次只追一个问题，例如：

> 为什么节点只返回 `{"count": 1}`，状态里的其他字段仍然存在？

推荐步骤：

1. 写最小实验。
2. 预测输出。
3. 运行并观察。
4. 查对应实现和测试。
5. 用自己的话写出解释。

问题解决后即可结束这一轮阅读，不必顺势读完整个文件。

## 4. 值得训练的思维方式

### 先设计数据，再设计流程

先列出状态字段、各字段由谁更新、什么时候更新，再画节点和边。让每个节点有清晰职责。

### 分清定义阶段与执行阶段

分别解释建图、`compile()` 和 `invoke()` 时发生了什么。阅读源码时，明确自己正在追踪哪个阶段。

### 把失败当作正常路径

主动实验超时、异常、中断和重复执行。涉及写数据库等操作时，思考重跑是否会重复产生结果，以及如何避免重复副作用。

### 用证据修正理解

运行前预测，运行后比较。看不懂就缩小示例，通过断点、状态输出和测试查原因。

### 按需要补基础

遇到 `TypedDict`、`Annotated`、生成器、`async/await` 时，做一个独立小练习，再回到项目。

## 5. 如何与 AI 一起学习

让 AI 检查你的理解，并保留自己推理和实践的过程。

可以这样提问：

> 先让我预测这个程序的状态变化，再检查我的解释；指出错误，并给一个最小反例。

也可以使用以下问题：

- 我认为这个节点会覆盖原有状态，我的理解对吗？请结合实现说明。
- 请给我一个只涉及条件分支的小练习，先不要提供答案。
- 这是我的运行预测和实际结果，请帮我定位理解上的偏差。
- 请检查我对 `compile()` 与 `invoke()` 的解释，指出遗漏。

## 6. 本地环境与版本注意事项

这个仓库是 monorepo，各库在 `libs/` 下，根目录没有统一的 Python 安装配置。

当前核心库配置要求 Python ≥ 3.10。完整开发配置包含 Unix 风格的 Makefile 和 `uvloop` 等依赖。在 Windows 上，第一阶段可以使用独立虚拟环境运行小实验，进入完整源码开发和测试阶段再考虑 WSL。

安装发布包后，调试进入的可能是 `site-packages`，未必是下载的源码。开始源码调试时，先确认解释器和实际导入路径。

相关文件：

- [核心库依赖配置](libs/langgraph/pyproject.toml)
- [核心库 Makefile](libs/langgraph/Makefile)
- [仓库贡献约定](AGENTS.md)

以后修改某个库的代码并准备创建 PR 时，按仓库要求在该库目录运行 `make format`、`make lint` 和 `make test`。

## 7. 今天的第一项任务

**写一个“检查文章 → 必要时修改 → 再检查”的图。**

任务约束：

- 使用固定规则模拟检查和修改。
- 最多修改三次。
- 记录每一步状态。
- 达标时提前结束；达到次数上限时也能结束，并保留检查结果。

验收清单：

- [ ] 能画出流程。
- [ ] 能说明每个状态字段的用途。
- [ ] 能预测一个简单输入的执行路径。
- [ ] 能解释为什么流程一定会结束。
- [ ] 能合上示例重新写一遍。
